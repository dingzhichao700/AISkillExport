# 自包含模板与导出规范

## 一、独立性的定义

普通导出只允许读取本仓库的 `Templates/GameFramework/ProjectFiles`，不得读取或克隆其他 Unity 工程。Unity Editor、Unity Package Registry 和可选 TexturePacker 属于软件依赖，不属于“外部工程依赖”。

`ProjectFiles` 不要求作为日常工程直接打开，但必须包含复制后生成一个有效 Unity 工程所需的全部源文件。

## 二、模板结构

```text
Templates/GameFramework/
└── ProjectFiles/
    ├── Assets/
    ├── Packages/
    │   ├── manifest.json
    │   ├── packages-lock.json
    │   └── com.code-philosophy.luban/
    └── ProjectSettings/
```

仓库不保存 Addressables 预构建缓存。`ProjectFiles/Assets/AddressableAssetsData` 是配置的唯一权威来源。

## 三、模板禁止项

- Unity 生成目录：`Library`、`Temp`、`Logs`、`UserSettings`、`obj`。
- IDE 产物：`.vs`、`*.sln`、`*.csproj`。
- 单次实验产物：bag、bagcartoon、baglegendary、shop、UIReference、AIUI 临时生成器。
- 外部工程路径、Golden/b1 克隆逻辑和机器专属默认路径。

## 四、导出契约

1. 运行模板静态验证。
2. 在系统临时目录建立 staging，不在最终目录制造 baseline 或中间工程。
3. 复制 `ProjectFiles` 到 `{ProjectName}/Project`。
4. 写入项目名称、AGENTS、docs、README 和 gitignore。
5. Unity 第一遍完成导入与编译。
6. Unity 第二遍执行 `GameFrameworkExportPipeline.ExportBaseline`，初始化并构建 Addressables。
7. 检查编译日志、成功 marker 和 bundle。
8. 全部通过后清理 `Library` 中可再生的导入与编译缓存，仅保留 `Library/com.unity.addressables` 的已验证构建产物。
9. 把瘦身后的 staging 移到最终输出路径。

目标已存在时默认失败；只有用户明确授权后才能使用 `-Force`。

## 五、Addressables 现场构建

每次导出都必须调用 Unity，根据当前 `ProjectFiles` 初始化、登记并构建 Addressables。不得提供跳过构建的参数，也不得复制旧的 `AddressableAssetsData`、catalog、settings 或 bundle；构建失败即导出失败。

Addressables 构建和编译验证必须在 staging 中真实执行，不能为了缩小交付体积而跳过。验证完成后，导出器应删除 `Library/BuildCache`、`Artifacts`、`PackageCache`、`Bee`、`ScriptAssemblies` 等 Unity 可再生缓存，仅保留 `Library/com.unity.addressables`。接收方首次打开工程时由 Unity 重新生成编辑器缓存。

上述要求针对“生成完整样例工程”的正式导出。已存在工程内的 AIUI 日常预览不属于完整工程导出：预览只同步变化的位图并生成可视 Prefab，不打图集、不登记或构建 Addressables，也不增删临时 C# 导出器。视觉定稿后再执行图集与绑定，发布校验时才登记并构建 Addressables；经用户确认，发布构建可留作人工步骤。

模板常驻 `Assets/Editor/AIUI/AIUIExportQueue.cs`，通过 `Library/AIUI/pending-preview.json` 接收预览请求。安装或升级工具本身允许发生一次编译和 Domain Reload；后续请求不得通过修改 `Assets` 下的脚本来触发执行。位图内容及导入设置未变化时，不得重复复制或调用 `SaveAndReimport`。

AIUI 定稿通过同一常驻工具的 `Library/AIUI/pending-finalize.json` 一次完成打图集、Prefab Sprite 引用替换和结构校验，并以 `finalize-result.json` 的状态与耗时作为完成依据。图集迁移应分别记录一次性工具编译、资源移动、源/目标图集重打、引用替换与校验耗时，不得把工具升级等待混入日常迁移耗时。不得使用 `Assets` marker 或解析 Editor.log 判断完成；请求 5 秒仍未消费时立即检查 runner/导入状态。普通内容定稿不重复执行 Skill 或完整模板校验，只有工具、模板或规范发生变化时才执行。

## 六、标准化回写

外部样例工程只在“标准化回写”中作为一次性、已验收的差异来源。回写前逐项确认可复用性；回写后运行静态验证，并在需要时从模板重新导出工程完成 Unity 验证。

禁止把游戏开发的定制化产物标准化回写，包括具体模块的资源清单、Prefab、业务代码、配置数据、模块名、图集名、资源名、目录实例、GUID、fileID、Addressables 条目或地址，以及单次请求、报告、测试数据和耗时结果。只允许回写从已验收产物提炼出的通用规则、参数化工具能力和不携带项目数据的实现。

## 七、验收标准

- 隔离或重命名所有外部样例工程后仍可导出。
- 新工程包含完整 Assets、Packages、ProjectSettings 和内嵌 Luban。
- Unity 编译与 Addressables 构建成功。
- 没有 Missing Script、Missing Sprite 或样例专属资源。
- `docs/docs` 不存在。
- `GameEntrance → Opening → Title → Option` 可正常运行。

## 八、启动初始化顺序

`RookieEngine.Awake` 必须先建立 UI 根、Timer 和对象池等核心服务，再调用 `PersistentDataControl.ReadUserSetting`，最后启动 `GameEntrance`。用户设置校正会同步派发分辨率、音量等事件，其中分辨率处理依赖 `RookieEngine.timer`；顺序倒置会在首次运行时触发空引用。
