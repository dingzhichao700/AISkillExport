# 游戏业务与配置规范

> 适用范围：基于模板开发的游戏业务模块，以及 Luban 配置从生成数据到运行时业务数据的接入。

## 一、业务 Model 与 VO

- 仅当模块存在业务数据管理需要时，才建立与模块同名的 `{Module}Model` 作为主要数据管理入口；不得为满足目录形式机械创建空 Model。
- 当数据管理职责过大、集中在一个 Model 中容易混淆时，可以按明确业务职责增加其他 Model。
- 单条业务数据对象命名为 `{Semantic}VO`，文件统一放入模块的 `model/vo/` 目录。
- Control 负责业务流程和权威状态修改；Model 负责数据集合、查询、初始化与存储边界；View 不直接修改 VO。

## 二、Luban 配置分层

- `CfgManager` 是统一运行时入口，负责使用 Addressables 已预加载的 JSON 初始化 Luban `Tables`、暴露表集合并在清理时释放资源。
- 仅当某张或某类配置存在重复使用的二次查询需求时，例如按类型取得配置列表，才在 `com/game/config/mgr/` 建立辅助管理类；不得为每张表机械创建 `CfgMgr`。
- `config/mgr` 只负责查询、筛选、索引或组合 Luban 原始映射对象，返回值仍应是 Luban 映射对象。
- 将配置转换为业务 VO、结合运行时状态构建玩法数据或实现玩法规则的逻辑，属于对应业务模块的 Model。

## 三、运行时加载顺序

1. 将所有需要运行时读取的 Luban JSON 名称登记到 `ResourceConst.ALL_CONFIG_LIST`。
2. Opening 阶段通过 Addressables 将列表中的 JSON 全部预加载到 `ResourceManager` 缓存。
3. 预加载完成后调用 `CfgManager.Init()` 创建 Luban `Tables`。
4. 业务模块只能在初始化完成后读取 `CfgManager.tables`；过早读取或缺少预加载资源必须显式报错，不得静默回退到磁盘或空数据。

## 四、新表接入流程

1. 设计并创建业务工作簿，登记到 Luban 总表。
2. 使用工程既有 Luban 命令生成 C# 映射类和 JSON，不手工修改生成文件。
3. 将生成 JSON 注册到正确的 Addressables Group，并加入 `ALL_CONFIG_LIST`。
4. 验证生成文件、JSON 行数、主键查找和代表性字段读取。
5. 按职责决定直接读取映射对象、建立按需 `CfgMgr`，或在业务 Model 中转换为 VO。

项目专属表结构、数值、业务 VO、玩法规则、测试断言和 Addressables 条目不得回写模板。
