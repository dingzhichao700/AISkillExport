# 通用构建与发布规范

## 边界和授权

通用工具链服务规范化样例工程，工程实例信息只放入工程配置。工程生成由 game-framework-toolchain 负责，构建发布编排由 game-build-release 负责，运行时协议和 Unity 平台实现随工程版本管理。

用户已明确的目标、环境和授权跨步骤沿用。检查、整理工具不授权发布；明确的构建发布请求覆盖约定的构建和发布步骤。发布不默认包含上传微信审核、改权限、删除历史内容或提交游戏源码。

## 版本和兼容性

- 构建类型必须明确记录。内容构建保留底座标识，底座重建生成新标识；PlayerSettings.bundleVersion 不承担 Catalog 命名。
- Foundation/AOT 代码、Unity/SDK/HybridCLR、原生插件、裁剪/桥接、编译宏、包内 JS、启动地址或缓存规则变化，需要评估并通常重建底座。
- 业务新增未被现有底座准备的类型、方法或泛型实例，同样可能要求更新底座。编译成功和源文件归属不能证明全部语义兼容。
- 不可变版本目录不覆盖；哈希 Bundle 同名复用前校验。保留旧客户端会话和历史 Catalog 依赖，不按文件年龄清理。

## 调度和失败处理

- 检查目标 Unity PID、工程路径、平台、协议版本、Play/编译/导入/运行状态。已有队列或非终态结果先核查，不能直接删除或重复提交。
- 请求先写临时文件再原子改名，结果必须匹配 requestId。操作终态、产物完整性和部署状态分别判断。
- 超时先保留现场，确认进程和队列状态；不自动重试会产生新版本的步骤。修复后明确从哪一步继续，不重复已成功发布的事务。
- 不关闭或重启用户的 Unity。无人打开工程时，按平台文档启动独立批处理或请用户打开；独立实例记录 PID 并正常退出。

## 发布顺序和隔离

1. 确定候选底座/内容版本，校验清单、Catalog、所有引用及底座匹配。
2. 部署不可变 Bundle 和内容目录，核验远端可访问与内容一致。
3. 更新本底座 current；需要发布入口映射时，最后合并更新 bootstrap，保留其他底座映射，并核验远端实际选中版本。
4. 如需新微信包，明确交付新的 minigame 目录；真机验收单独报告。

共享存储按 `<共享根>/<项目名>/` 隔离。发布前从工程配置确认目标前缀，上传和指针更新只操作该项目；不得将桶根作为单项目发布目录。COS 的命令、上传校验和缓存响应头见 [COS发布流程](COS发布流程.md)。

多项目资源仓库提交只包含本项目和本次版本，不能 git add 全仓库。推送包含全部待推送提交：提前检查分支及待推送历史，不能只检查本次暂存文件。推送成功不代表 Pages 已部署；有异步部署时等待其完成并检查 HTTP 实际内容。

## 归档和回退

底座构建后，在项目 build 下以底座标识归档：工程源码/依赖版本及脏改动快照、编译设置、启动配置、HybridCLR 设置、热更新 DLL、裁剪后 AOT、桥接/保留文件、构建状态、包体及文件哈希。记录资料来源；缺少对应资料时不能假装可以重建历史底座。

可再生目录进入 Git 忽略不等于允许丢弃历史资料。归档属于产物管理，不把 DLL、缓存、发布实例或密钥写入通用 Skill。

回退只操作明确的兼容底座：验证历史 manifest/Catalog/Bundle 完整，记录当前指针，按同样的部署核验流程切换到历史 manifest。不会替换已经运行的程序集，客户端重启后生效。当前脚本提供历史版本只读校验，指针变更由会话按明确回退请求执行，不调用 publish-local 误发最新构建状态。

## 完成标准

分别记录候选构建、本地指针、远端资源、远端指针、包体交付、开发者工具验收和手机扫码验收。记录需关联底座/内容版本、包路径、验证日期及证据来源（工具结果或用户反馈）；用户反馈通过只能覆盖其明确验收范围。缓存复用、兼容内容更新与回退未单独验证时不能标记通过。说明未执行项；不以日志无报错、Unity 编译通过或下载变快替代完整运行验收。

工具维护先用临时夹具、只读工程检查和 dry-run 验证。不得以测试为由触发实际发布。当前以对话驱动，不自动创建 Jenkins 或其他后台调度。
