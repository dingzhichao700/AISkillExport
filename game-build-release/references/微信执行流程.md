# 微信执行流程

## 读取现状

使用目标工程配置和 inspect 输出，不预设雷电战机路径。读取工程的微信平台规范；新模板已含 HybridCLR/Remote Addressables 实现，老工程先核对已有适配。

队列协议 v1 位于 Project/Library/AIUI：wechat-build-ready.json 提供 PID/target，editor-status.json 提供状态，pending-wechat-build.json 接收请求，wechat-build-result.json 返回 requestId/status/error/outputPath。状态文件必须来自当前进程；怀疑过期时检查注册器，不按窗口标题推断。

## 首次构建与 WebGL 切换

默认新模板已带微信依赖、宏、程序集引用及热更新列表；不应重复执行平台接入。旧 Standalone 工程先按用户授权执行工程 Tools/Set-GameFrameworkPlatform.ps1；保留工程参数，不复制案例的 AppID/CDN。

切换 WebGL 属于本 Skill。目标工程已由用户打开时，使用已有编辑器控制能力切换，等待导入完成再检查队列；没有控制能力则请用户在 Build Settings 切换，不另开争用实例。目标工程未打开时，使用匹配 ProjectVersion 的 Unity，以 `-batchmode -nographics -buildTarget WebGL -projectPath <路径> -logFile <项目build下日志> -executeMethod FrameworkWeChatBuild.RunBatch -frameworkAction prepare` 启动隐藏的独立进程；后续 generate/export 同理。不要加 -quit，RunBatch 在完成时退出。记录 PID，按 requestId/退出码/产物确认结果。启动前验证工程无占用且已填写项目参数。

首次 prepare 安装与本机 Unity 配套的 HybridCLR 运行时；模板只保存配置，不复制别的工程的 HybridCLRData、底座版本、AOT 或已编译 DLL。命令被执行策略拒绝时报告原始拒绝信息，不通过拆命令或替代入口绕过。

## 构建

通用命令：`Invoke-GameBuild.ps1 -ProjectPath <Unity工程> -Action <动作>`。先可加 `-WhatIf`。

| 动作 | 含义 | 成功终态 |
|---|---|---|
| prepare | 安装项目内 HybridCLR 并设置热更新程序集 | prepared |
| generate | 生成新底座标识、桥接/AOT/DLL | generated |
| export | 构建微信包和候选资源 | exported |
| content | 保持底座，仅构建业务 DLL 和资源候选 | content-built |
| publish-local | 更新本地 current/bootstrap，不上传远端 | published-locally |

新底座按 prepare（缺失或配置变化时）、generate、export 顺序执行；兼容内容执行 content。每一步等待同一 requestId 的成功终态；failed/error 立即停止后续步骤。不要将本地 publish 的历史命名理解为已部署远端。

构建后运行 `validate_release.py --project <路径>`。校验对应包内底座、manifest、settings 的直接 Catalog 定位、无 hash 依赖、Bundle 路径边界和文件存在；存在对应 ServerData 文件时比对 SHA256。sourceHashesCompared 少于 bundles 时明确哪些源文件不在本地，不宣称完成全部原始文件哈希比对。

## Git Pages 发布

用户要求发布且 deployment 配置完整后：

1. 确认仓库根、发布分支、remote、项目目录和待推送历史；使用路径限定检查 Git 状态。遇到其他已暂存改动或未知待推送提交，不擅自一并发布。
2. 候选验证通过后，仅暂存本项目本次 releases/<版本> 和新增 bundles。检查暂存 diff 无覆盖、删除或其他工程内容，中文提交信息，推送明确 remote/branch。
3. 等待 Pages 部署完成。读取远端新 manifest/settings/Catalog，并核验当前 Catalog 引用的 Bundle；下载大文件校验可用现有 HTTP/文件工具，说明校验覆盖范围。不可访问时不切指针。
4. 执行 publish-local，使用 --published 再核验；仅暂存本项目 current/bootstrap，独立提交推送。
5. 等待第二次部署完成；带防缓存参数请求 bootstrap/current，核对目标底座与内容版本。失败时保留产物、记录哪一步未完成，不宣称远端已生效。

拆成两次部署是为了先确认不可变资源可用，再公开发布指针。已有本地指针修改不应混入第一次提交。其他 CDN 使用相同顺序，不能直接照抄 Git 命令。

## 缓存及交付

底座标识和 bootstrapUrl 来自包内启动配置；一次启动固定内容版本。Remote Bundle 使用虚拟根映射到同底座共享 bundles，settings/Catalog 映射到 releases/<版本>。不依靠 catalog.hash 选版本。

真机允许缓存不可变版本 Catalog 和哈希 Bundle，bootstrap/current 保持更新；开发者工具缓存可能不同。微信插件 DATA_CDN 与 Addressables 资源定位职责不同，不擅自删 SDK 字段。Skill 接入不得修改现有缓存规则或客户端虚拟根。

报告匹配底座的包路径、内容版本和远端核验结果；按[构建发布规范](构建发布规范.md)“客户端底座核对与真机交付”确定手机操作与记录范围。手机首次启动、保留缓存二次启动、同底座内容更新分别验收；不把换包生效或工具链自检当作同底座热更新通过。

## COS 部署

当 deployment.kind 为 cos 时，远端候选上传与指针发布采用 [COS发布流程](COS发布流程.md)，不执行 Git Pages 的提交、推送或 Pages 状态检查。Unity 队列、候选校验和归档要求相同。
